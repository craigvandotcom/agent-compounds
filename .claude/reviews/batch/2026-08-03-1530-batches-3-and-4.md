## Critical — both fixed

### C1. `uninstall_precommit_guard` called with an argument the live tool does not accept
`skills/ac-land/SKILL.md`

The new harm-scoped uninstall rule (ac-zqj, `1c8257a`) instructed
`uninstall_precommit_guard(project_key, code_repo_path)`. **Verified against the live MCP tool
schema:** `uninstall_precommit_guard` takes `code_repo_path` (+ optional `format`) only —
`project_key` is required on the *sibling* `install_precommit_guard` and does not exist on the
uninstall tool. The call as written would have errored at the exact teardown step the bead
added. Copied by analogy from the installer.

**Fixed:** call corrected, with the asymmetry called out inline so it is not re-introduced.
Net-zero on the file (see gate note below).

### C2. The new Tier-1 CI assertion could not distinguish a passing run from a failing one
`skills/ac-batch-close/SKILL.md` — Act 1, "Assert this gate; never assume it"

The block added by `ac-batch-close-ci-gate-vacuous-adbq` (`3668748`) states the green condition
as "**(i) an executed run** — completed, successful, head SHA == the batch anchor", then gives a
verification command that filters on `headSha` alone:

```
jq -r --arg s "$ANCHOR" '[.[] | select(.headSha | startswith($s))] | length'
```

A **failed** run for the anchor SHA yields `1`, satisfying the "nonzero → the gate ran" test the
prose uses to license reporting `Tier 1 CI: green`. `--json headSha,conclusion` already requested
`conclusion` and then never used it — an omission, not a design choice. This reproduces the exact
vacuous-gate class the commit was filed to close, which is why it is Critical rather than High.

**Fixed:** `and .conclusion=="success"` added to the filter; the surrounding prose now states
that the conclusion filter *is* the assertion, and that `0` means "no run PASSED" (none ran, or
one ran and failed) — neither licensing green.
